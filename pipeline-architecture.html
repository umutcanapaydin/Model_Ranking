General Pipeline v4.1

Architecture & Technical Design Document

Document status: RATIFIED · Increment 11 · 2026-07-30 · Supersedes the architectural sections of pipeline-design.md §2 · §11

What this document is. A structural specification of the pipeline as a system: its components, the interfaces between them, where enforcement physically happens, what the data model is, where the trust boundaries fall, and how the whole thing is allowed to change. It is not a tutorial (see START_HERE.md), not the rule reference (pipeline-design.md), and not the visual overview (pipeline-schema.html). Where those describe what to do, this describes how the machine is built and why it holds together.

1Purpose, scope and non-goals

1.1 The system in one paragraph

General Pipeline is a delivery methodology packaged as an executable artifact. It ships as a directory that a new project copies wholesale: machine-read house rules, a default-deny permission matrix, reviewer role definitions, executable quality and security gates, document templates, and the scripts that enforce them. Around that package runs a five-stage workflow plus a maintenance loop. Around that runs a governance layer: every rule in the package traces to a recorded incident, and changes to the rules are ratified by a blind multi-role AI council whose minutes are themselves machine-validated records.

1.2 Goals

#GoalHow the architecture serves it
G1An AI agent with no memory of this project can produce correct, reviewable work on day oneAll state lives in committed files with a defined read order; no session state is authoritative (§7, §10)
G2Quality claims are mechanically verifiable, never self-assertedThe evidence rule: anything feeding a gate is computed from git/CI against protected refs (§9, §11)
G3The owner keeps meaningful control without reviewing every lineRisk tiers + the autonomy ladder pinned at A0.5, with escalate-NOW as an interrupt channel (§7)
G4The process itself improves from evidence rather than opinionHarvest → register → blind council → ratified cut, with an append-only trail (§13)
G5Nothing requires standing infrastructureZero services: files, git, make, CI, and three pinned Python packages (§2, §17)
G6Every control can be shown to workConformance fixtures + a CI self-test that fails when a rule stops firing (§9.4)

1.3 Non-goals — stated so they stop being re-proposed

  • Not an orchestrator. The pipeline does not schedule agents, own a run queue, or hold execution state in a service. Agent invocation belongs to whatever harness the operator uses.
  • Not a runtime. There is no daemon, no controller, no message broker, no database. See §17 for the reasoning and the re-open triggers.
  • Not a judge of prose. The system validates the shape of records, never the truth of a rationale or the soundness of a review. Schematising judgement produces theatre (§10.4).
  • Not a product. There is no multi-tenant story, no plugin API, no backwards-compatibility promise to third parties.

2Architectural drivers

2.1 Hard constraints

IDConstraintArchitectural consequence
C1One owner, not full-time on tooling; no platform team, no on-call rotationZero standing infrastructure is a hard constraint, not a preference. Failure ownership dominates every build-vs-adopt decision.
C2The operators are language modelsFluency is an operational requirement. A format an agent can author and repair unassisted beats a more expressive format it will subtly break twice a year (§17).
C3Agents are non-deterministicAny mechanism whose correctness depends on replay determinism is unsound here (§17). Trust must be computed from outcomes, never from agent narration.
C4Portability across agent harnessesNo harness-specific state may be load-bearing. Rules live in AGENTS.md-class files; continuity lives in committed files.
C5Everything must be abandonable in an afternoonFormats over tools; owned scripts over dependencies; deletion must leave valid markdown and a working repository.

2.2 Quality attributes, ranked

Ranked deliberately: when two conflict, the higher one wins, and that ordering is what makes the architecture predictable.

  1. Verifiability — a claim that cannot be checked mechanically has no standing. Drives §9 and §10.
  2. Inspectability — a human must be able to audit any decision in minutes, from files, without tooling. Drives the markdown-first record model.
  3. Reversibility — every control must be removable without leaving the repository broken. Drives §17 and the two-cut deletion rule.
  4. Portability — survives a harness change, a machine change, a three-day gap.
  5. Throughput — deliberately last. The system will trade speed for verifiability, and says so.
Driver → design, the single most consequential line: because C3 says agents are non-deterministic and driver 1 says claims must be verifiable, no agent statement may ever be a gate input. That one implication generates the evidence rule, the git-derived telemetry, the fresh-eyes reviewer, the citing-test requirement, and the owner's out-of-sandbox verification. Nearly every distinctive part of this architecture descends from it.

6Control plane versus work plane

The sharpest structural line in the system. The control plane is data; the work plane is code. They live in the same repository, are edited by the same agents, and are governed by opposite rules.

Control plane

Rules, permissions, reviewer profiles, records, schemas, gate definitions.

  • Read from the protected base ref, never from the change under evaluation
  • Append-only; supersede rather than edit
  • Machine-validated for shape (§10)
  • Changing it requires a governance record, not just a commit
  • Path-protected by CODEOWNERS so a change cannot self-approve

Work plane

Product source, tests, project docs, deployment manifests.

  • Read from the working tree — that is the point
  • Freely rewritten within a wave
  • Validated by tests and reviews, not by schema
  • Changing it requires a wave, a review and a citing test
  • Sensitive paths (⛔ globs) escalate the review tier automatically
The invariant that keeps them separate (V4C-06). Any policy consumed by a reviewer, a gate or an agent is resolved from the protected base ref — never from the branch, comment or task under evaluation. Without this, a change can rewrite the rules that judge it in the same commit. Three separate 2026 exploits in the wider industry did exactly that: credential theft through issue comments, a review bot reading its instructions from the head branch, and a single pull request escalating to remote code execution across a million repositories.

7Runtime view — the life of a wave

7.1 Risk tiering — how review depth is selected

tier(diff) is computed, never asserted by the agent:
  LOW   ≤150 LOC · no ⛔ glob · no dependency/schema/CI change   → ONE combined reviewer
  MED   ≤600 LOC · logic across ≤3 modules · no ⛔ glob          → Code-Reviewer + Tester
  HIGH  any ⛔ glob · >600 LOC · deps/schema/public API change   → both + security pass on the slice
                                                                  + owner as required reviewer

one-way ratchet: the tier may rise during a wave, never fall.
anti-gaming: cumulative merged LOC per task counts, so splitting a HIGH task into
many LOW pull requests escalates anyway.

7.2 The autonomy ladder, and where it is pinned

LevelWave closeCommitsStatus
A0Owner reviews every waveOwnerSuperseded by A0.5
A0.5Agent-side: fresh-eyes reviews + green checks pinned to the closing tree + committed checklistOwner, at milestone cadence, plus a labelled checkpoint commit per waveACTIVE (PROVISIONAL)
A1 / A2Agent closes and commits to mainAgentNORTH STAR — NOT ACTIVE. Requires an explicit owner ADR. The protocol document carries a binding banner.
Bright line. An agent committing to main is A1. There is no gradual path into it, no "just this once", and no configuration flag: it takes a recorded owner decision. The architecture enforces this socially and mechanically — agents have no git credentials in this lane.

Why intake is a failing test and not a ticket. A bug description is prose and decays; a red test is an executable specification that cannot drift from the defect. It also makes the fix's completion criterion mechanical — the wave is done when that specific test is green and no earlier.

9Enforcement architecture

This is the layer most systems get wrong, because declaring a check and enforcing one look identical in a document and are entirely different in a repository.

9.1 Why exactly one aggregate check

The git host reports a skipped required job as success, and a status name can be written by any app unless the check is bound to a specific one. Both facts turn a conditional required check into advice wearing a badge. The architecture therefore keeps a single unconditional aggregate job as the required check; individual jobs beneath it may be conditional, because the aggregate cannot be.

# .github/workflows/governance-contract.yml  (root of the repository)
jobs:
  governance-contract:            # unconditional · never continue-on-error
    steps:
      - Validator self-test       # FIRST: proves the validator is not a no-op
      - Validate records          # fields, refs, cycles, propagation
      - Historical scan           # informational; prior versions are FROZEN
      - Fake-pin check            # a /blob/main/ URL called a "pin" tracks HEAD

# actions are SHA-pinned, and both SHAs were verified against the host API at adoption —
# a pin you did not verify is a superstition.
Operator precondition. This file does not create authority by existing. Until the check is marked required on the protected branch, bound to the intended app, with bypass disabled and its own path protected, it is Tier 2. The architecture cannot self-install its own enforcement — and pretending otherwise is the failure this whole layer exists to prevent.

9.2 Fail direction — the control-class rule

Control classFailsRationaleRequirement
Authentication, authorisation, safetyCLOSEDAn unavailable check must not become an open doorMust ship a tested disable switch, and must emit an operator-actionable reason
Fairness, rate limiting, quotasOPENDegradation beats denial of service to legitimate usersMust be observable when open
Governance validationCLOSEDAn unparsed record is an unknown recordUnrecognised values fail; silence is never assent

A fail-closed control that gives no reason is a diagnosability defect, not a success: behaviour indistinguishable from a bug will be treated as a bug, at 3 a.m., by someone with less context than you.

9.3 Where each gate physically sits

Stage 0  bootstrap-check      local + CI      BLOCKING  no project work before green
Stage 3  wave-check           local + CI      BLOCKING  per wave close
Stage 4.0 security review     human + tools   BLOCKING  before any deploy
Stage 4.1 citing-test rule    CI              BLOCKING  milestone does not close

repo     governance-contract  CI aggregate    GATE      records must validate

9.4 Validating the validator

A control nobody has watched fail is a control nobody has. The conformance corpus applies the pipeline's own fault-injection protocol to its enforcement code:

conformance/
  pass/   3 fixtures   the smallest records that MUST validate clean
  fail/   9 fixtures   one per blocking rule, each declaring its expected diagnostic:
                       <!-- expect: X3 -->

$ make check-records-selftest
  self-test ok: fail/dangling-ref.md → X1
  self-test ok: fail/status-ahead-of-dependency.md → X3
  ...
  self-test PASS: 0 problem(s)

Adding a blocking rule REQUIRES adding its failure fixture in the same change.
On its first execution this corpus found a real defect in the validator:
cross-record rules never fired in single-file mode.

10Record data model

Governance records are markdown files with a validated frontmatter block. The prose stays canonical; the frontmatter carries only the facts a machine consumes.

10.1 Frontmatter schema

# schemas/record.schema.json · JSON Schema 2020-12 · additionalProperties: false
record_type   ratification | register | adr | experience | handover | design | council
id            ^[a-z0-9][a-z0-9.\-]{2,63}$        unique across the repository
status        draft → candidate → ratified → superseded → retired   ordered flow
--- optional, each consumed by a specific check ---
process_version  ^v[0-9]+(\.[0-9]+){0,2}$
supersedes[]     resolves to a real id · cycle-checked
requires[]       dependency edges · drives status-flow ordering
subject_ref      commit SHA the record describes
propagation[]    artifact + expected_version + status   a `pending` row fails
evidence_ref     pointer into git/CI output
approvers[]      NON-AUTHORITATIVE — author-written, never treated as authorization
date             ^\d{4}-\d{2}-\d{2}$

10.3 Blocking scope — current version only

Prior packages are frozen by the versioning rule, so a finding inside one is history, not a defect to fix. The validator blocks on the current package and surfaces the rest through --historical. This is why general_pipeline_v3.3 still reports its missing heading: repairing it would violate the never-edit-a-prior-version rule, and the finding is more useful as evidence than as a fix.

10.4 The narrowness rule — the anti-bloat control for the data model

A field may exist only if a check consumes it. Every required field must answer: "which concrete failure does its absence permit?" Fields unused for two cuts are deleted. This exists because the alternative is well documented: a forty-field record gets completed with plausible filler, and filler that validates is worse than a blank.

11Trust boundaries

11.1 Credential custody

  • GP lane: agents hold no git credentials at all. The owner performs every commit and push; this is a property of the lane, not a policy an agent could violate.
  • GDF lane: CI holds all credentials. Agents trigger workflows; they never possess a token, an SSH key or a registry password. A CI check greps agent workspaces for secret patterns.
  • Journey probes: credentials are minted short-lived and CI-held, never stored in the script, never printed — not even in a failure path.
  • v4.1 direction: the credential ledger records identity, scope and expiry per credential name. Recording is not isolation; enforcement is a pilot-exit condition (§19).

13Versioning and propagation architecture

13.1 Semantics

BumpMeansExample
MAJORLane or stage topology changes, or the governance model itself changesv4.0 — first externally-informed evidence class; constitution mechanics on the ballot; both lanes in one council
MINORAdditive rules within the existing topologyv4.1 — repairs plus the record-validation layer
PATCHWording, typos, non-semantic fixesreserved

13.2 The superset rule

v2.0 ⊆ v2.1 ⊆ v2.2 ⊆ v3 ⊆ v3.1 ⊆ v3.2 ⊆ v3.3 ⊆ v3.4 ⊆ v3.5 ⊆ v4.0 ⊆ v4.1

A new version is COPIED FORWARD and only the new copy is edited.
A prior package is never modified — not for a typo, not for a defect.
Verified mechanically at every cut: zero files may be missing from the predecessor.

Deliberate exception, recorded: the presentation deck is versioned, not accumulated.

The cost of this rule is disk space and some duplication. The benefit is that any past claim can be reproduced exactly, which is what makes the decision trail auditable rather than merely narrated.

13.3 Propagation — from prose to mechanism

A version bump touches artifacts that must move together. Until v4.1 that list was a prose checklist, and it failed in the field: a patch helper consumed a changelog heading and nobody noticed for two weeks. Now the coupling is declared as data and checked:

propagation:
  - pipeline-schema.html   expected v4.1  done
  - pipeline-design.md     expected v4.1  done
  - AGENTS.md              expected v4.1  done
  - executive-overview     expected v4.1  pending    ← this row FAILS the gate

plus two invariants asserted directly against the tree:
  P2  every package retains its §0 changelog heading
  P3  the overview's file count equals the real file count

Ordering rule at a cut: the overview is regenerated LAST, because it counts files.

14The two-lane split and the pin architecture

GDF is a sibling lane in a separate repository, for work where the requirements are still fuzzy and speed matters more than ceremony. It is architecturally interesting for one reason: it consumes the constitution by reference, never by copy.

General_Pipeline (repo)                 General-Distributed-Flow (repo)
  general_pipeline_v4.1/     ◄────pin────  GDF-CONSTITUTION.md
    the constitution                          §1 inherited core (pinned to v4.1)
    evidence rule                             §2 overrides — ONE PAGE MAX
    security baseline                            OVR-1..4, each with its rationale
    escalate-NOW class                        if the appendix outgrows a page,
    files-not-sessions                        that is the drift alarm

Pin discipline: a signed charter records which version it pinned. Charters signed
before a re-pin KEEP their original pin — pinned means pinned. The N1 rule exists
because a pin expressed as a /blob/main/ URL is not a pin at all.

What GDF overrides

  • Agents merge, behind mechanical gates — GP's A1 bright line is consciously crossed for this lane only, and the decision record says so in plain text
  • Review is a risk-tiered ephemeral bench mapped to required status checks
  • The owner reviews asynchronously, protected by backpressure caps, tripwires and auto-freeze

What it may never override

  • The evidence rule
  • Default-deny permissions and the security baseline
  • The escalate-NOW class
  • Credential custody: CI holds them, agents never do
  • The base-pinned policy invariant
An architectural lesson worth the whole lane. GDF's task-claim mechanism assumed the tracker offered an atomic claim. It does not: the vendor closed that feature request as won't do in 2015, and the documented update path is read-modify-write with no precondition. Two agents can both claim one task and the last write silently wins. The claim is now described accurately, one builder per domain is the interim rule, and the replacement — creating a git ref as a genuine server-side compare-and-swap — is a pilot, because it is novel and unvalidated. Verify platform guarantees against the primary document; the word "atomic" is free in a design doc.

15Maturity placement and the deliberate ceiling

RungTest — you are on this rung if…Us
1 · Prose conventionsIgnoring the instructions still produces a merge with no machine-detectable violationwhere our records were before v4.1
2 · Prose + executable gatesAt least one gate is a program that can fail a build, but the records are unparsedwhere the package was
3 · Records as validated dataEvery governance record is parsed against a declared schema in CIv4.1 — here now
4 · Cross-record invariantsCI fails when records are individually valid but mutually inconsistent, and propagation is machine-checkedpartially: X1–X3 and P1–P3 exist; the remainder is Phase 2
5 · Executed, stateful, traced engineA runtime owns event history and run identity and enforces transitionsREFUSED BY DECISION — not deferred by budget
The stopping rule. Do not climb a rung because the ladder has another rung. Advance only when a measured failure at the current rung demands it. Rung 5 is refused because no published project governs its own process on such an engine, and because our real failure mode is "a step was skipped and nothing noticed", which no runtime solves. Re-opening it requires an owner decision record with evidence that rung 4 is insufficient.

19Known limitations

1 · The gate is not yet in force. governance-contract exists and passes, but until it is marked required on the protected branch, bound to the intended app, with bypass disabled and its own path CODEOWNER-protected, it operates at Tier 2. This requires an operator action outside the repository, and the architecture cannot perform it for itself.
  • The permission matrix is a claim, not a check. Reconciliation against live branch protection and code-owner settings is Phase 2. Today the document and the platform can diverge silently.
  • Local hooks are opt-in. Every hook is mirrored in CI by rule, so nothing depends on them — but a reader could mistake the hook configuration for enforcement. It is not.
  • Two validator copies. The repository root and the package each carry check_records.py. They must stay in step until the shared SHA-pinned workflow lands, and nothing currently enforces that.
  • No resume contract yet. "Continuity is files" is correct and confirmed by research, but it names no required fields. A six-field minimal contract is adopted and scheduled; today a handover can describe history without naming the next action.
  • Package accretion. 95 to 115 files in one minor version, mostly fixtures and decks. Recorded honestly; controls that never fire get deleted under the two-cut rule.
  • The delegated lane has never run. Eight rules now sit on a machine with no pilot behind it. Further pre-pilot rule additions are frozen by council ruling.
  • No measured benefit exists, anywhere. All three architecture passes independently reported that nobody publishes before-and-after outcomes for governance validation. Our own measurement window, closing 2026-10-30, will be the only evidence on the question — and it is pre-registered, including its failure conditions.
