DevFlow · the pipeline, one page

From a design to a merged change, and every gate on the way

Seven stops. The agent plans, builds, reviews and opens drafts; a human approves plans and merges pull requests. A red signal is a stop that refuses — a check that blocks, or a person who has to approve. An amber one reports straight back to the agent.

the agent opens drafts · a human merges one issue per unit of work two separate reviewers every wave no AI attribution anywhere
0

Bootstrap

once per project
  • The tools for your OS — Windows, or macOS / Linux — then the common steps: INSTALL.md. An existing repository takes DevFlow's files by its rules, which overwrite nothing of yours.
  • /setup-project asks the owner nine setup questions — new, upgrade or adopted; Quality Gate on or off; retrospective; HIGH-risk areas and their reviewer; deploy; what the repo can enforce; the CI issue agent; the product's stack and language — and writes docs/project-brief.md, .devflow-stack and .language-allow.
  • Name the project in pyproject.toml.
  • make install — records the installed version in .gp/installed.
  • make hooks — once per clone: make gate runs before every push.
  • make labels — creates the issue labels every skill keys on; touches none that exist.
  • A stack other than python: its lint, typecheck, test and deps legs bound in stack.mk.
  • Branch protection on the default branch (docs/branch-protection.md).
make bootstrap-check — Stage 0 does not close with placeholders left, or with no push gate where nothing else enforces
make install-check — every file the install needs is present
1

Plan the milestone

/plan-milestone
  • Writes docs/plans/m{N}-plan.md: goal, REQ-ID criteria, risk tier, waves, contracts, budget, issue inventory.
  • Issues: searches open and closed first. A match is recorded and left untouched; only work with no issue gets one created.
  • Opens the plan as a draft PR on plan/m{N}.
The owner approves the plan by merging it. No wave starts before.
2

Build the wave

branch wave/m{N}-w{W} · parallel subagents
  • Each agent runs a dev-test loop on its slice: implement → test → self-review → fix.
  • A reported symptom is reproduced as a failing test before it is fixed.
  • Big exploration goes to the read-only Explorer (.claude/agents/Explorer.md).
Guards refuse: writes to .env, git reset --hard, force-push, rm -rf, git checkout -- or git restore over uncommitted work, a push to the default branch — and every call they cannot read, when no working Python is on PATH
After every edit: make check-fast — the legs of make check, side by side, offline; red goes straight back to the agent
3

Close the wave

/close-wave · every wave, every risk tier
1 · code-reviewerits own subagent, fresh eyes · .claude/agents/Code-Reviewer.md · writes docs/reviews/m{N}-wave-{W}-review.md
2 · testera second, separate subagent · .claude/agents/Tester.md · citing tests, fault injection · writes docs/reviews/m{N}-wave-{W}-tester.md
  • BLOCKING → fix on the branch, then a new reviewer. The author never reviews its own wave.
  • HIGH-risk wave: a security pass on the slice as well.
  • Fill the wave checklist (docs/wave-checklist.template.md), open the wave's draft PR, run /pre-merge.
make wave-check — refuses unless both verdicts exist and neither is BLOCKING
/pre-merge runs make gate — the full gate, network legs included
A human merges, then /post-merge
↻ back to stop 2 until every wave in the plan has merged
4

Close the milestone

docs/closure-checklist.md · nothing deploys here
  • Capture: process log, decisions via /log-decision, seeds, the EXPERIENCE entry, the AGENTS.md diet.
  • No retrospective and no handover during the work.
  • Quality Gate — optional, off by default. The owner turns it on in the brief; then the closure report docs/closure-report-m{N}.md is written.
Every wave in the plan merged
If the Quality Gate is on: make closes refuses a criterion with no citing test, or not ✅
5

Release

once, when the work is done
  • Security review of the whole release (.claude/agents/Security-Reviewer.md) — verdict in docs/reviews/release-security.md.
  • Deploy + go-live: /going-live — the running build is the built one, each dependency answers, a human path works.
  • Retrospective — optional: /cycle-close — what went right, where we got stuck, which controls earned their place.
Security review BLOCKING before anything deploys
make cold-start · make smoke-deps · make journey — "the build passed" is not "the thing running is right"
6

Maintain

after go-live · fix waves + fixpack
  • A production bug becomes a failing test first; the fix only turns it green.
  • Fixes ship as a fixpack (docs/fixpack.template.md) — the deploy gate for fixes.
Owner verifies outside the sandbox before the fixpack deploys
Issues

Three ways work arrives

Planned

  • /plan-milestone gives each unit one issue
  • waves resolve them; each wave's PR lists its issues

Found along the way

  • /file-issue — search first; comment on a duplicate, never edit it
  • /triage-issue ends with one line: Triage verdict: fix-issue, work-issue or work-enhancement

Worked

  • /fix-issue — safe to automate: red test, fix, the Tester alone (fresh eyes), draft PR
  • /work-issue — a human in the loop
  • /work-enhancement — several phases, one PR
  • after merge: /post-merge — a bug stays open with dev:done until QA
